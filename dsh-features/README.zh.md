# dsh-features

[English](README.md) | 中文

本仓功能插件的统一入口：侧栏一项「功能管理」，在「插件」与「自动化任务」之间。它的页面把每个已安装的
功能插件就地挂载进同一个外壳、风格统一，不再有一堆浮动按钮压住 dsh 界面。

它自己不是功能，而是其余 `dsh-*` 包挂靠的基座：页面、侧栏图标与样式是一份浏览器 bundle
（`lib/client.js`），由 dsh 自己的客户端模块系统加载——这是加一个真正的导航项的**唯一**途径。
它不依赖任何其它插件，其它插件不装它也照常工作。

## 安装

```bash
dsh plugin --profile web add github:LBurny/dsh-plugin#path:/dsh-features
```

`--profile web` 是 DSHDesktop 壳，`--profile desktop` 是官方桌面版；插件面板里装则不用带参数。
装完重启 dsh（插件没有 HMR）。

## 它做什么

- **侧栏一项真导航。** `sidebar.panellist`，`order: 5`；官方两项是「插件」（`0`）与「自动化任务」
  （`10`），该槽位按 `order` 排序。
- **一页承载所有功能。** 每个已安装的功能插件一行，和 dsh 自己的「插件」页一样（图标、名称、说明、
  箭头）。**点进去**才是该功能的设置页，头部有返回控件。卡片可拖拽排序，顺序存在 `localStorage`
  （`dsh-features:nav-order`）。**整页只有一个刷新控件**，在页头：它重扫清单、重挂当前功能，
  并问每个安装来源是否已经前进（见下面的**更新**）。窄屏（<620px，手机远程视图）收窄边距。
- **能看见、也能应用的更新。** 某个包的来源已经越过 profile 钉住的提交时，那一行带上**可更新**，
  页头出现一个汇总的更新按钮。没点那个按钮之前，什么都不会装。
- **统一外观。** 样式表隐藏 `#dsh-launchers`，并复用各功能面板已经在用的 `--dsh-*` 调色板，
  所以同一个功能在内嵌与浮窗里长得一样。颜色优先取壳的主题令牌（`--dsw-alias-*`，跟随 dsh 的
  深浅色设置），取不到才退回硬编码值。
- **失败也有名字。** profile 声明了、但浏览器半边没加载成功的功能会标成「已安装，但面板没加载」，
  而不是悄无声息地消失。注意「声明了」才是关键：只把包放进 `<DSH_HOME>/profiles/plugins/<名字>/`
  不算安装，也不会出现。
- **名字跟着语言走。** dsh 的插件页把它列成**功能管理**或 **Features**，而不是包名，靠的是包里的
  `locale/en.json` 与 `locale/zh.json`（见下面的**显示名**）。

## 更新

页头那个刷新控件一次做两件事：重扫清单，以及问每个已安装功能的安装来源是否已经前进。

- **检查**（`GET /dsh-features/api/updates`）。一个包从哪来是 profile 的记录，不是包自己的：规格在
  `<profile>/package.json`，pnpm 解析出来的提交在 `<profile>/pnpm-lock.yaml`。拿该来源做一次
  `git ls-remote` 就知道它动没动，按仓库去重而不是按包，所以同一仓的多个包只花一次往返。`link:`
  依赖就是活的源码，永远不算落后；`file:` 副本按它自己声明的版本比；registry 版本一律报成未知，
  不猜。联系不上的来源会写在页面上，不会把整次检查弄失败。
- **应用**（`POST /dsh-features/api/update`）。`pnpm update <包名>`，走插件管理器自己的 pnpm runner，
  包在它的事务里，所以这里的更新不会和插件页的安装交错。只接受本 profile 装着的包。检查本身
  不装任何东西：它只给行加一个标记、给页头加一个按钮，第二次点击才真的写。
- **要重启。** 插件没有 HMR。路由应答时新文件已经在盘上，但运行中的 dsh 还是旧代码，重启后才生效。
- **基座自己也在这个名单里。** 本包和其它包一样从某个来源安装，但它不是功能，所以没有自己的行、也没有
  标记。检查与应用都把它算进去（插件页没有更新它的办法），页面上也会写明，免得按钮上的数字比标记多一个。

为什么不是重装同一个规格：`pnpm add <同一个规格>` 不会重新解析，它打印
"Lockfile is up to date, resolution step is skipped" 然后原地不动，所以重装更新不了任何东西。
`pnpm update <包名>` 会重新解析 git 规格，带 `#path:/<子目录>` 的也算。两条都在 2026-10-11 实测过：
App 运行时里的 pnpm 11 与独立的 pnpm 12。

检查只在读者要的时候跑，绝不在页面加载时跑。结果留在宿主进程里，随清单一起下发，所以检查之后才打开的
页面同样显示这些标记，不用再问一次。

## 显示名

dsh 的插件页从包本身取名字，不加载它。`locale/en.json` 是这套文件的锚点，同目录其它文件按语言 id 命名，
各自带 `meta.title` 与 `meta.description`（这就是 dsh-app-boot 的 `readPluginMeta`，包详情与组件行
用的是同一条路）。本包带 `locale/en.json` 与 `locale/zh.json`，所以列出来是**功能管理**或
**Features**，说明文字也跟着语言走。

两个细节都会静默失败：这些文件是按包的 `exports` 解析的，所以有 locale 目录却没有 `"./locale/*.json"`
这一条，等于没有元数据；`en.json` 是锚点，缺了它别的语言根本不会被读。没有元数据时 dsh 退回包名，
这就是一个插件在 诊断、任务提醒 旁边显示成 `dsh-features` 的原因。

## 两条约定

除这两条外一切独立：没有共享模块，不 import 任何兄弟包。

**1. 功能把自己发布给基座**——这是它能出现在列表里、以及基座怎么挂载它的方式：

```js
window.__dshFeatures = Object.assign(window.__dshFeatures ?? {}, {
  doctor: {
    title: "诊断",                      // 侧栏标签（功能自己已本地化）
    icon: "M2 8.5h3l1.5-4 2.5 7 ...",   // 可选：16×16 描边 SVG path
    order: 60,                          // 默认顺序（读者的拖拽顺序优先）
    mount(host) { /* 渲染进 host */ }     // 每次进入都调用；必须可重挂
  }
});
```

**2. 功能为清单声明同一份信息**（只是元数据，让基座能报出脚本加载失败的那个功能）：

```json
"dsh": { "ui": { "feature": {
  "key": "doctor", "order": 60,
  "title": { "zh": "诊断", "en": "Doctor" },
  "summary": { "zh": "运行状态与日志尾部", "en": "Status and log tail" }
} } }
```

功能启动时还会探一下 `GET /dsh-features/api/status`：基座应了，它就不在自己角落挂按钮（界面已经能从
基座页到达）；路由不在（没装基座，或 profile 里没有这个包）时，浮窗照原样建起来。所以卸载本包，
浮动按钮就回来了。

## 测试

```bash
cd "$DSH_HOME/profiles/plugins/dsh-features"
node tests/hub.test.mjs
```

该套件会真跑浏览器半边（vm + 极简 React），所以侧栏槽位、顺序、皮肤、列表、钻取、拖拽顺序、
挂载交接，以及更新那一半（标记、按钮、它发的 POST、一次检查的三种结局）都不用浏览器就能断言。
仓根还有一个跨包套件：`node tests/panel-embed.test.mjs`。

## 已知边界

- 检查要调 `git ls-remote`，所以 dsh 启动时的 PATH 里得有 `git`。没有的话每个 git 来源都按联系不上
  报出来，附 git 自己的话；页面照常工作。私有来源不会弹凭据提示（`GIT_TERMINAL_PROMPT=0`），
  所以它是报错而不是卡住。
- 更新替换的是运行中的 dsh 已经加载过的文件，所以结论是要重启，也是检查与应用分成两次点击的原因。
